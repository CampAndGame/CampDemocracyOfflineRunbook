# Диагностика WS/таймера/звука на стенде Democracy — установка и использование

Инструмент для разбора жалоб вида «нажимаю показать вопрос — таймер/звук
запаздывает». Показывает, в каком слое теряется время (сервер / сеть / браузер),
и в большинстве случаев сам называет причину.

## Состав (что вам передали)

| Файл | Что это |
|---|---|
| `diag.html` | страница диагностики, отдаётся nginx'ом по `/diag` |
| `democracy-service-1.0.40-amd64.tar.gz` | api: + STOMP-heartbeat каждые 4с (нужен для «пульса» соединения; всё остальное как в 1.0.39) |
| `democracy-admin-standalone-0.0.4-amd64.tar.gz` | админка: + телеметрия в `/client-log` и логи таймингов в консоли (функционально не менялась) |
| `DIAG-SETUP.md` | этот файл |

## Установка

### 1. Образы

```bash
docker load < democracy-service-1.0.40-amd64.tar.gz
docker load < democracy-admin-standalone-0.0.4-amd64.tar.gz
```

В своём `docker-compose.yml` поменять теги:
- сервис с образом `.../democracy-service:` → тег `1.0.40`
- сервис с образом `.../democracy-admin-standalone:` → тег `0.0.4`

(если теги заданы переменными `${VERSION:-...}` / `${ADMIN_VERSION:-...}` —
поменять дефолты или экспортировать переменные).

### 2. Nginx: страница /diag и приёмник телеметрии /client-log

`diag.html` положить рядом с compose-файлом. В сервис **nginx** добавить volume:

```yaml
    volumes:
      - ./diag.html:/etc/nginx/diag.html:ro
```

В конфиг nginx (server-блок, рядом с остальными location) добавить два блока:

```nginx
    # Страница диагностики
    location = /diag {
        default_type text/html;
        alias /etc/nginx/diag.html;
    }

    # Телеметрия из браузеров (админка шлёт сюда бекон-запросы;
    # строки остаются в access-log nginx-контейнера)
    location = /client-log {
        return 204;
    }
```

### 3. Перезапуск

```bash
docker compose up -d
```

Нюансы:
- при последующей правке `diag.html` на месте нужен `docker restart` nginx-контейнера
  (single-file bind-mount не подхватывает замену файла на лету), браузер жёстко
  обновить (Ctrl/Cmd+Shift+R);
- при старте api в логах одноразово мигнёт Flyway-миграция — это нормально.

## Использование

### Страница /diag

Открыть `http://<стенд>/diag`, ввести пароль админки, «Войти и проверить».
Держать открытой (активной вкладкой!) во время игры.

Вердикты:
- **WebSocket-транспорт** — красный = WS-апгрейд не проходит, приложения падают
  в polling, события идут пачками. Чинить проксирование WS в nginx
  (`Upgrade`/`Connection`).
- **REST-задержка** — медиана > 500мс = тормозит железо/БД стенда.
- **Троттлинг вкладки** — красный = браузер душит фоновую вкладку. То же самое
  происходит со вкладкой админки, если она в фоне — её звук и таймер будут
  запаздывать. Держать админку активной вкладкой в отдельном окне.
- **Ровность тиков** — интервалы серверного таймера (норма ~1000мс). p95 > 1300мс
  = сервер тикает рвано.
- **Доставка сервер→клиент** — задержка каждого события по его серверному
  timestamp (рассинхрон часов вычитается сам). p95 > 700мс = сеть/прокси буферит.
- **Пульс WS** — сервер (api >= 1.0.40) шлёт heartbeat каждые 4с; «тишина Nс» =
  связь или сервер зависли.
- **JVM сервиса** — GC-паузы/CPU/heap с `/actuator/prometheus`. GC > 300мс
  подсвечивается и пишется в лог прямым текстом «вот причина рваных тиков».

**Автодиагноз** — блок под вердиктами: собирает все метрики и пишет вывод
человеческим языком («GC-паузы — поднять память», «вкладка в фоне», «сеть
буферизует», «всё в норме»). Дайте поработать минуту-две.

**Live-лог** — каждое WS-событие игры с точным временем, `lat=` (доставка) и
`Δ=` (интервал тиков).

**«Скачать лог»** — выгружает вердикты + автодиагноз + все события в .txt.
Нажать сразу после инцидента и отправить файл разработчику.

**«Тест показать вопрос»** — активный замер полного цикла (команда → звук →
пре-старт → старт времени) с авто-скрытием через 5с. ⚠ Съедает ~5 секунд
времени активной команды — на живой игре не жать.

### Телеметрия админки (ретроспективно, ничего открывать не надо)

Админка 0.0.4 сама шлёт диагностические бекон-запросы, они оседают в логе
nginx-контейнера. Посмотреть после инцидента:

```bash
docker logs democracy-ui 2>&1 | grep client-log
```

Что там:
- `src=admin-ws&ev=<тип>&lat=<мс>` — задержка приёма события вкладкой админки.
  Тикающие события (TIME/PRE_START_TIME) попадают сюда только при lat > 500мс —
  само их появление уже симптом.
- `src=admin-sound&ev=<звук>&note=playing&ms=<мс>` — сколько прошло от приёма
  события до фактического старта звука.
- `note=blocked&err=NotAllowedError` — браузер заблокировал автоплей: после
  открытия админки нужен хотя бы один клик по странице.

В консоли браузера админки (F12) те же данные живьём: `[demo-ws] recv ... lat=`
и `[demo-sound] ...`.

## Как читать типовые случаи

| Симптом | Причина |
|---|---|
| всё зелёное на /diag, но в client-log посыпались `TIME lat=1500+` | вкладка админки в фоне — держать активной в отдельном окне |
| `admin-sound playing ms=1000+` при маленьком lat | тормозит аудио на ноуте админки (декодер/устройство вывода) |
| `admin-sound blocked NotAllowedError` | автоплей заблокирован — кликнуть по странице админки |
| тики рвано + JVM: GC max сотни мс | мало памяти api — поднять mem_limit контейнера и heap в JAVA_OPTS |
| тики рвано + JVM: CPU > 85% | процессор стенда перегружен — смотреть docker stats всех контейнеров |
| тики ровные, но «Доставка» p95 сотни мс | сеть/прокси между сервером и браузерами |
| транспорт красный | nginx: локация WS без Upgrade/Connection → SockJS в polling |
| «Пульс: тишина Nс» | обрыв/зависание WS — сеть площадки, рестарт api |
| задержка 0–1с «то есть, то нет» на старте таймера | норма: серверный тикер раз в секунду, клик попадает в случайную фазу |

## Что прислать разработчику при инциденте

1. Файл с кнопки «Скачать лог» (если /diag была открыта).
2. Вывод `docker logs democracy-ui 2>&1 | grep client-log` за период инцидента.
3. `docker logs democracy-api --since <время>` (если по п.1–2 виновата серверная сторона).
